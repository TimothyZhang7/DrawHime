# 代理约束

本文件是处理 `aiimage/` 任务时的硬约束。旧版长文档已备份，当前版本只保留必须执行的规则。

## 必读顺序

1. `README.md`
2. `AI_INDEX.md`
3. 本文件
4. 与任务相关的 `docs/*.md`
5. 与任务相关的源码

## 代码规则

- 所有新增或修改的源码必须有中文注释。
- 每个新增源码文件必须有中文文件级职责注释。
- 导出函数、导出类、接口/DTO、配置 schema、数据库脚本入口必须有中文注释。
- 鉴权、余额、QQ 绑定、充值、绘图重试、事务、回滚、数据清理、生产部署等关键分支必须有中文注释。
- 不允许用假数据、伪接口、占位逻辑绕过真实业务。
- 不允许为了通过构建而绕过鉴权、余额、绑定、权限、错误处理。
- 单文件建议控制在 600 行以内；已超出文件优先拆分，不继续堆逻辑。

## 接口规则

- 跨程序请求、响应、WebSocket 事件、队列任务类型必须先登记到 `standards/interfaces/README.md`。
- 类型落地到 `packages/shared-contracts` 后，业务程序只能从 `@aiimage/shared-contracts` 导入。
- 成功响应默认使用 `{ ok: true, data: ... }`。
- 失败响应默认使用 `{ ok: false, code, message }`。

## 数据规则

- 数据库独立于旧系统。
- 余额归属是身份钱包：Web 用户钱包和 QQ 钱包独立存在，绑定只共享可访问余额，不迁移、不合并钱包。
- 卡密和 token 类数据只保存哈希，明文只允许在一次性响应或私有文件中出现。
- 涉及余额、卡密、QQ 绑定、任务状态最终写入必须事务化或幂等。
- 图片先落本地或对象存储，再回写业务记录。

## 前端规则

- `main.tsx` 必须保留样式入口导入。
- 修改路由、入口、全局 CSS 后必须构建验证。
- 全局轮询必须检查登录状态，避免未登录 401 刷屏。
- 管理后台和用户前台不得绕过 backend 权限逻辑。

## 命令执行规则

- 读取文件前先用 `rg --files` 或 `Test-Path` 确认真实路径，不得凭经验直接读取可能不存在的文档。
- 固定文本搜索默认使用 `rg -F`；只有确实需要模式匹配时才使用正则，复杂表达式必须拆成可独立验证的小命令。
- 多个互不依赖的只读命令可以并行；其中任一失败仍需保留其他输出时必须使用可收集全部结果的调用方式，禁止让单个失败吞掉整批诊断结果。
- PowerShell 调用 SSH 时，复杂远端脚本必须通过标准输入发送多行脚本；禁止把 PowerShell、Shell、JavaScript 三层插值压成一个不可审计的单行命令。
- 轮询网络和 GPU Runtime 必须捕获瞬时超时，使用有上限的重试、退避和总截止时间；单次 `fetch` 失败不得直接判定服务故障。
- 生产查询只输出任务 ID、状态、模型、尺寸、步数和耗时等必要字段，禁止打印用户提示词、参考图、令牌、完整队列载荷或私有环境变量。
- 任一命令出现语法、路径、参数或网络错误后，必须先修正根因并重新通过该步骤，禁止带着未解释的失败继续部署或提交。
- 禁止重复执行等价的全仓检查：开发阶段运行受影响目标的最小检查，部署脚本已经包含的完整检查只执行一次。

## 完整执行链路

1. 读取规范、确认仓库与适用文档，执行 `git status --short`，只记录本次范围和无关改动。
2. 阅读真实调用链后再修改；跨程序契约先更新接口登记和共享类型。
3. 修改后执行 `git diff --check` 和受影响目标的最小 `type-check/test/build`，失败立即修复并重跑。
4. 部署前检查 `git diff`、目标服务和活动任务；默认运行 `node scripts/quick-deploy.mjs --changed --dry-run` 自动选择最小端点，不得打断不可恢复的运行中任务。
5. 默认执行 `node scripts/quick-deploy.mjs --changed`；只有基础设施或明确跨全端变更才允许 `--all`，不得为了省事全量构建或重启。
6. 部署后验证目标 `/health`、必要的 `/ready` 或 `/health/db`、公网入口和关键业务状态，查询结果必须最小化和脱敏。
7. 只有部署及验证全部成功后，才用明确路径 `git add <path...>`，再次执行暂存区 diff 检查并创建本地提交。
8. 需要同步公开仓库时只复制已部署源码和文档，比较文件一致性后单独提交并推送，生产凭证、媒体、权重和用户数据不得进入公开仓库。
9. 最终报告必须包含实际改动、验证、生产状态、提交 SHA；跳过的检查必须说明真实原因。

详细命令和错误复盘见 [docs/operations.md](docs/operations.md)。

## 部署规则

- 纯文档、约束或说明修改默认不重启生产运行服务，只完成本地验证、提交和公开源码同步；用户明确要求发布文档时再同步生产源码目录。
- 所有代码或配置修改完成后默认部署到生产，并按受影响端点验证；只有用户明确要求“只本地修改”或“不要部署”时才跳过部署。
- 生产端口使用 `6369/3005/3004/3011/3012/3013/3014/3015/3016`，不得回退到旧系统端口。
- 生产凭证不得写入文档或提交说明。
- 部署前按 [docs/deployment.md](docs/deployment.md) 检查。
- 每次生产部署完成并通过验证后，必须在本地 git 创建一次提交，提交内容只包含本次已部署的源码、配置样例、文档或脚本变更，用于确认该次部署实际更新内容。
- 如果工作树存在与本次部署无关的改动，提交时必须使用明确路径只暂存本次部署文件，不得顺手提交或回滚用户的其他改动。
- 部署失败或验证未通过时不得创建“已部署”提交；必须先修复并重新完成部署验证。
